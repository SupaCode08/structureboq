## 2. สมมติฐานเดิมของขั้น 3 และผลทดสอบ: **ไม่ผ่าน**
สมมติฐาน: OCR แค่บางบรรทัดเพื่อสอนตัวอ่านรูปตัวอักษร (`glyphRead.ts`) แล้วอ่านที่เหลือด้วยการจับคู่รูป

จำลองจาก OCR ใน cache (บนสำเนา/สคริปต์ใน scratchpad; เทียบกับ OCR เต็ม ไม่ใช่เฉลย — วัดความตรงกับ OCR ไม่ใช่ความแม่นยำ) บนหน้า 24–28, 37–39:

| 100% ของหน้านั้นเอง | 123/694 (18%) · เบอร์ 30/44 · โน้ตเหล็ก 0/4 |
| 50% | 11% · เบอร์ 18/44 |
| 25% | 2% · เบอร์ 0/44 |
| 10% / 5% | 0% |

ข้อจำกัดของการทดสอบ: โน้ตเหล็กมีแค่ 4 ตัวอย่าง และ OCR ที่ใช้เป็นตัวเทียบมีข้อผิดเอง (เช่น "3@16") จึงยืนยันได้แค่ว่า **ตัวอ่านรูปตัวอักษรปัจจุบันเรียนรู้ช้าเกินกว่าจะแทน OCR ได้** ไม่ได้พิสูจน์ว่าวิธีจับคู่รูปทำไม่ได้เลย
**สรุป: ไม่ควรสร้างขั้น 3 แบบนี้**

## 4. ทางเลือกที่ยังเหลือ (ยังไม่มีหลักฐานว่าคงความแม่นยำ — ต้องวัดก่อนเลือก)
| ทางเลือก | คาดว่าลดอะไร | ความเสี่ยง | วิธีวัด |
|---|---|---|---|
| A. ลดความละเอียด render (ตอนนี้ 300 DPI) | เวลา OCR ลดตามพื้นที่ภาพ | ตัวอักษรเล็ก (สูง ~5.8 pt) อ่านผิด/หาย | ต้อง OCR ซ้ำจริงที่ DPI ต่าง (ใช้ FULL_BOQ) แล้ว eval บนสำเนา |
| B. OCR เฉพาะกล่อง (ROI) รอบละหลายบรรทัด แทนทั้งหน้า | ตัดพื้นที่ว่าง/เส้นก่อสร้าง | วางกล่องผิด | ต้องวัดเวลา/ความแม่นยำจริง; มี `ocrLabels` (OCR ทีละบรรทัด) อยู่แล้ว opt-in — ยังไม่เคยวัดว่าเร็วหรือแม่นกว่า |
| C. ลด engine จาก 2 ตัวเหลือ 1 บางหน้า | ลด CPU ต่อหน้า | ตัวที่สองอาจช่วยหาตัวเลข/โน้ตเหล็ก | ใน cache ไม่มีป้ายว่าคำมาจาก engine ไหน ต้อง OCR ซ้ำแยก engine |
| D. อ่านหลายหน้าพร้อมกัน (worker) | เวลารวมตามจำนวน core | 4 รอบต่อหน้าแย่ง CPU อยู่แล้ว อาจได้ไม่มาก | วัดบนเครื่องจริง |
| E. ข้ามหน้าที่ไม่ใช่โครงสร้าง (ข้อ 2 ของแผน) | ลดจำนวนหน้า | ข้ามหน้าที่ต้องอ่าน | วัดกับ page classifier; ผู้ใช้ยืนยันเอง |

## 5. ข้อเสนอ
1. **ยกเลิกขั้น 3 เดิม**, ย้ายไปวัดทางเลือก A–C ทีละข้อ
2. ลำดับ: **E** (ถูกและปลอดภัยสุด) → **A** → **B** → **C** → **D**
3. ด่านทุกข้อ: `eval_reading` ชุดพัฒนา ไม่มีค่าถูกเปลี่ยนเป็นผิด/ไม่พบ, `check:full` บนสำเนา scratchpad ไม่ regress, held-out วัดอย่างเดียว; ถ้าเร็วขึ้นแต่เสียความแม่นยำ ให้ revert
4. เป้า 10 วินาที: **น่าจะไปไม่ถึงสำหรับหลายหน้าที่ต้อง OCR เต็ม** ด้วย 4 รอบ/หน้า (~10 วิ/หน้า) ถ้าไม่ได้ A/B หรือเครื่องเร็วกว่านี้ — ต้องคุยว่าเป้านับกี่หน้า และเปิดครั้งแรกหรือใช้ cache

- ไม่ได้ทดสอบ: หน้า scan, production build, E (ข้ามหน้า) ในเชิงความแม่นยำ, parallel ในเบราว์เซอร์ (วัดใน Node เท่านั้น)

### 8.6 วัด DPI ซ้ำ ทุกหน้าโครงสร้างของ 3 บ้าน (49 หน้า, re-OCR จริงใน Node, scratchpad, 2026-11-06)

| DPI | ถูก / ผิด / ไม่พบ รวม | tag ถูก | count ผิด | rebar ถูก / ผิด | ค่าที่ผิดต่อบ้าน (1 / 2 / 4) |
