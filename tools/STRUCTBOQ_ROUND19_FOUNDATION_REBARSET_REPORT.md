### คำตอบ 5 ข้อ
1. **รองรับหลายกลุ่มบางส่วน:** ได้ ≤2 กลุ่ม ขนาดต่างกันได้ ทิศสมมติตามลำดับ (มี flag) — ชั้นเดียว รูปงอเดียว
2. **Engine รับหลาย RebarSet ได้หรือไม่:** โครงรองรับ — `pushBarItem` คิดทีละกลุ่มแล้วรวมตามขนาดอยู่แล้ว เปลี่ยนเฉพาะ "ที่มาของกลุ่ม" (จากข้อความ → จากชุด) ไม่ต้องแก้สูตรความยาว/น้ำหนัก
3. **Data model เก็บทิศ/การจัดได้หรือไม่:** **ไม่ได้** — ต้องเพิ่มฟิลด์
4. **ฟิลด์ที่ต้องมีเพื่อคิดอย่างปลอดภัย (ต่อชุด):** ขนาด; จำนวน **หรือ** ระยะเรียง; ทิศ (X/Y/ทั้งสอง — ไม่จำเป็นเฉพาะจำนวนคงที่บนฐานจัตุรัส); ชั้น; รูปปลายทั้งสองข้าง + ความยาวงอ (ถ้างอ); ต่อชิ้น: กว้าง/ยาว/หนา, ระยะหุ้ม
5. **ใช้ระบบเดิมซ้ำ:** `approvalKey` ครอบ `rebarSets` อัตโนมัติ (แก้ชุด → approval ชิ้นหลุด); คลาส B ใช้กลไก 18c ได้ตรง (flag ที่ผูก field `rebarSet:<id>`); ป้ายที่มาใช้ `FieldSource` + `SOURCE_BADGE` เดิม; ตรา by/revision 18d ใช้เดิม

## 2. ข้อจำกัดทางสถาปัตยกรรมที่ต้องตัดสินก่อน

| # | ข้อจำกัด | ข้อเสนอ |
|---|---|---|
| L1 | **approval อิสระต่อชุด** (ผู้อนุมัติ/เวลา/revision แยกต่อชุด) ไม่มีในระบบ — approval มีระดับชิ้นเท่านั้น | ใช้แบบ 18c: แต่ละชุดมีที่มาของตัวเอง (`source`) และ "ยืนยันชุด" = `source: reviewer` + ตรา `confirmedBy/at/revision` บนชุด; อนุมัติชิ้นได้เฉพาะเมื่อทุกชุดยืนยัน/มาจากแบบครบ (คลาส B) → ยืนยันชุด A ไม่ยืนยันชุด B ✅ แต่ "อนุมัติ" สุดท้ายยังเป็นระดับชิ้น — **ไม่ทำ approval record แยกต่อชุด** (จะเป็นการเปลี่ยนโครงสร้างใหญ่) |
| L2 | reader ไม่รู้ทิศ | **ไม่แก้ reader** ในรอบนี้ (แก้แล้วต้องรัน `check:full` บนสำเนา + ความแม่นยำการอ่าน) — ชุดเหล็กสร้างจากหน้าตรวจทาน: ปุ่ม "แยกเป็นชุดเหล็ก" แปลงข้อความเดิมเป็นชุดที่ **ทิศ = UNSPECIFIED** (ไม่เดาทิศ), เก็บข้อความต้นฉบับใน `sourceText`, ที่มา = ที่มาเดิมของ `rebar` |
| L3 | แก้เรขาคณิตแล้ว "การยืนยันชุด" ควรหลุดหรือไม่ | approval ระดับชิ้นหลุดอยู่แล้ว (valuesKey) — การยืนยันชุดยืนยัน "สิ่งที่แบบเขียน" (ขนาด/ระยะ/ทิศ) ไม่ใช่ตัวเลขที่คำนวณ จึง **คงไว้**; ปริมาณที่คำนวณใหม่ต้องอนุมัติชิ้นใหม่ |
| L4 | `arrangement` ในโจทย์มี `TWO_DIRECTION` ซ้อนกับ `direction: BOTH` | ใช้ `arrangement` = วิธีกำหนดจำนวน (`FIXED_COUNT`/`SPACED`/`UNSPECIFIED`) และ `TWO_DIRECTION` = ข้อความเดียวที่หมายถึงทั้งสองทิศ (บังคับคู่กับ `direction: BOTH`; คู่อื่น = ขัดแย้ง → flag) |
| L5 | รูปงอ 12d / งอเต็มความหนาเป็นค่าสากลในทางเดิม | ในชุดเหล็ก: `UPTURN` (ตั้งขึ้น) ความยาวไม่ระบุ → คิดจาก ความหนา − 2·cover (เรขาคณิต ติดป้าย "คำนวณจากความหนา" info) · `HOOK_90` ความยาวไม่ระบุ → **ชุดนั้นคิดไม่ได้ (BLOCKED)** ไม่ใช้ 12d · `UNSPECIFIED` → คิดเหล็กตรง + flag คลาส B |

## 3. แผนการแก้ (ไฟล์และการเปลี่ยนแปลงที่แน่นอน)

### 3.1 Data model — `qsEngine.ts` (เพิ่มเท่านั้น, optional)
```ts
export interface RebarSet {
  id: string;                                   // 'RS-' + สุ่ม base36 ครั้งเดียวตอนสร้าง; ทำซ้ำ = ID ใหม่
  diameterMm?: number; barType?: 'DB' | 'RB';
  arrangement: 'FIXED_COUNT' | 'SPACED' | 'TWO_DIRECTION' | 'UNSPECIFIED';
  quantity?: number; spacingMm?: number;        // ไม่แปลงหากัน
  direction: 'X' | 'Y' | 'BOTH' | 'UNSPECIFIED';
  layer: 'BOTTOM' | 'TOP';
  startHook: HookEnd; endHook: HookEnd;         // 'NONE' | 'UPTURN' | 'HOOK_90' | 'UNSPECIFIED'
  hookLengthM?: number;                         // undefined = ไม่ทราบ (ไม่ใช่ 0)
  cuttingLengthM?: number;                      // ถ้าแบบให้ความยาวตัด ใช้แทนการคำนวณ
  sourceText?: string;                          // ข้อความต้นฉบับจากแบบ (เช่น "3-DB12 + 3-DB12 @150")
  source: FieldSource;                          // drawing / reviewer / assumed / missing / inferred
  confirmedBy?: string; confirmedAt?: string; revision?: string;
}
// ExtractedMember: rebarSets?: RebarSet[]
```
- **ไม่มี `rebarSets`** → engine ใช้ทาง `bottomRebar` เดิมทุกอย่าง (ตัวเลข/flag เหมือนเดิม — approval ที่บันทึกไว้ไม่หลุด เพราะ `approvalKey` ข้ามฟิลด์ที่เป็น undefined)
- **มี `rebarSets`** → engine คิดจากชุดเท่านั้น; `bottomRebar` คงไว้เป็นข้อความต้นฉบับ (ไม่ใช้คำนวณ)
- `reviewStatus`/`calculationStatus`/ระดับ provenance ต่อชุด = **ค่าที่คำนวณได้** (ไม่เก็บซ้ำ): ส่งออกใน `rebarDetails.sets[]`

### 3.2 สูตร — สาขา FOOTING ของ `computeDetailedRebar`
ฟังก์ชันใหม่ `footingRebarSetBars(set, geometry, cover)` คิดชุดละครั้ง → ใช้ `pushBarItem` เดิม (ความยาว = ช่วงหักระยะหุ้ม + ปลายสองข้าง; น้ำหนัก = ตาราง `REBAR_KG_PER_M` เดิม) — **ไม่มีสูตรความยาว/น้ำหนักใหม่**
- X: เหล็กยาวตามกว้าง วางกระจายตามยาว; Y กลับกัน; BOTH/TWO_DIRECTION = สองแถว (X และ Y)
- SPACED: จำนวน = ⌊(ช่วงกระจาย − 2·cover)/ระยะ⌋ + 1 (สูตรเดิม) — **ไม่ปัดขึ้นเป็น 3** (ไม่มี clamp ในทางชุด)
- คิดไม่ได้ → ชุดนั้น `BLOCKED` + flag `block` ระบุชุด (เก็บอินพุตไว้, ไม่รวมน้ำหนัก, ชิ้นอนุมัติไม่ได้)

### 3.3 Validation ต่อชุด (flag มี `field: 'rebarSet:<id>'`)
| เงื่อนไข | ระดับ | คลาส |
|---|---|---|
| ขนาด ≤0/ไม่มี, จำนวนไม่ใช่จำนวนเต็มบวก, ระยะ ≤0, ระยะ < ขนาดเหล็ก, ความยาวตัด/งอติดลบ, HOOK_90 ไม่มีความยาว, เหล็กไม่พอดีหน้าตัด (จำนวน×ขนาด > ช่วงสุทธิ) | block | C (แก้ชุดแล้วผ่านได้) |
| arrangement กับฟิลด์ขัดกัน (FIXED_COUNT ไม่มีจำนวน, SPACED ไม่มีระยะ, มีทั้งสองแต่ไม่ตรงกัน, TWO_DIRECTION + ทิศเดียว) | block | C |
| ทิศ UNSPECIFIED (คิดได้เฉพาะจำนวนคงที่บนฐานจัตุรัส; นอกนั้น block) | warn / block | B |
| arrangement UNSPECIFIED, ปลาย UNSPECIFIED | warn | B |
| ที่มาชุดไม่ใช่ drawing/reviewer (assumed/missing/inferred) | warn | B |
| ไม่มีชุดเลยแต่ `rebarSets: []` | block | C (ห้ามคิดเหล็กเป็น 0 เงียบ) |
- คลาส B ทั้งหมดเข้า `fieldsApprovalCannotCover` เดิม → อนุมัติชิ้นไม่ครอบจนกว่าชุดนั้นถูกแก้/ยืนยัน

### 3.4 UI — ไฟล์ใหม่ `src/components/FootingRebarSets.tsx` + `ReviewWorkspace.tsx`
- ในหน้ารายชิ้น เมื่อเป็นฐานราก: การ์ดต่อชุด (ขนาด มม., จำนวน เส้น, ระยะ มม., ทิศ, การจัด, ชั้น, ปลายต้น/ปลาย, ความยาวงอ ม., ความยาวตัด ม., ข้อความต้นฉบับ, ป้ายที่มา, สถานะคำนวณ, flag ของชุดนั้นใต้การ์ด) + ปุ่ม เพิ่ม/ทำซ้ำ/ลบ/ยืนยันชุด + ปุ่ม "แยกเป็นชุดเหล็ก" (จากข้อความเดิม, ทิศ UNSPECIFIED)
- แก้ผ่าน `draft` เดิม → `decide()` เดิม → `onUpdateMembers` เดิม (ตรา by/revision 18d ทำงานเหมือนเดิม); ชุดที่แก้ → `source: reviewer`
- `SectionTable` (ตามเบอร์): ไม่แก้ — engine กักคลาส B อยู่แล้ว จึงอนุมัติชุดที่ไม่แสดงไม่ได้
- `ManualCalculator`: **ไม่แก้** (ชิ้นที่เพิ่มเองไปแก้ชุดเหล็กต่อในหน้าตรวจทานได้)

### 3.5 Audit trail — `reviewLog.ts`
เพิ่ม `rebarSets` ใน `TRACKED_FIELDS` (เทียบด้วย JSON, แสดงเป็นสรุป `RS-xxx: 4-DB12 X …`) — การแก้/ลบ/ทำซ้ำชุดเข้าประวัติและ undo ได้ด้วยกลไกเดิม

### 3.6 Export — `excelWorkbook.ts`
แผ่น "ตารางดัด-ตัดเหล็กเสริม": เพิ่มคอลัมน์ RebarSet ID, ทิศ, การจัด, ระยะเรียง (มม.), ชั้น, ที่มา/ระดับ provenance, สถานะชุด, ข้อความต้นฉบับ, **"ยอดชั่วคราว (รอตรวจ)"** สำหรับ NEEDS_REVIEW; ชุดที่ BLOCKED ส่งออกเป็นแถวน้ำหนัก 0 พร้อมเหตุผล (ไม่หายไป); ชื่อแผ่น/หมายเหตุคงคำเตือน "ห้ามใช้สั่งตัดเหล็ก" (ไม่ใช่ BBS อนุมัติ)

### 3.7 เทสต์ — `src/engine/rebarSet.test.ts` (ใหม่, เพิ่มใน `npm test`)
ครอบหัวข้อ 1–35 ของโจทย์ที่ทดสอบได้ระดับ engine/export/log; เทสต์เดิมทั้งหมดต้องผ่านโดยไม่แก้ (ทางข้อความเดิมไม่เปลี่ยน)

### 3.8 Migration
ไม่มี migration — `rebarSets` optional; โครงการ/รีวิวเดิมคิดและกู้คืนเหมือนเดิม; ชิ้นที่แยกเป็นชุดแล้ว approval ชิ้นเดิมหลุด (ตั้งใจ: ค่าที่ใช้คำนวณเปลี่ยน)

## 8. การคำนวณ (`rebarSetBars`, สาขา FOOTING ของ `computeDetailedRebar`)
- **ลำดับ:** คิดทีละชุดทีละทิศ แล้วรวมตามขนาดด้วย `pushBarItem` เดิม **ไม่มีสูตรความยาวหรือน้ำหนักใหม่** และไม่แตะทางข้อความเดิม
- **ทิศ:** X คือเหล็กยาวตามความกว้าง วางกระจายตามความยาว; Y กลับกัน; BOTH คิดเป็นสองแถว
- **ระยะเรียง:** จำนวนเส้น = ⌊ช่วงสุทธิ/ระยะ⌋ + 1 (สูตรเดิม) ทางชุด**ไม่ปัดขึ้นเป็นขั้นต่ำ 3 เส้น**
- **ปลายเหล็ก:**
  - ตรง: 0
  - งอตั้งที่ไม่มีความยาว: ความหนา − 2×cover (เรขาคณิต ติด flag info)
  - งอฉากที่ไม่มีความยาว: **คิดไม่ได้** ไม่ใช้ 12d
  - ไม่ระบุ: คิดเป็นปลายตรง ติด flag คลาส B
  - ความยาวตัดที่แบบให้มา: ใช้ตามนั้น
- **ชุดที่คิดไม่ได้:** เก็บอินพุตไว้ น้ำหนักเป็น 0 ติด flag `block` ทำให้อนุมัติชิ้นไม่ได้ แต่ชุดอื่นยังคิดต่อ ถ้าไม่มีชุดเลยจะ block ด้วย `REBAR_SETS_EMPTY`

## 10. Provenance และการอนุมัติ

**ระดับ provenance ต่อชุด** (`rebarSetProvenanceLevel`)
- reviewer: USER_CONFIRMED (ไม่ยกเป็น DRAWING_VERIFIED แม้ไฟล์เป็น DXF)
- ชิ้นที่ไม่มี provenance: UNKNOWN
- drawing + DXF: DRAWING_VERIFIED
- drawing + OCR/ข้อความ: OCR_EXTRACTED
- assumed/inferred: ENGINEERING_ASSUMPTION
- missing: DEFAULT_VALUE

**คลาส B ใหม่:** `REBAR_SET_SOURCE`, `REBAR_SET_ARRANGEMENT_UNSPECIFIED`, `REBAR_SET_HOOK_UNSPECIFIED`
- การอนุมัติทั้งชิ้นไม่ครอบชุดเหล่านี้จนกว่าชุดนั้นจะถูกแก้หรือยืนยัน
- ข้อความระบุ "ชุดเหล็ก RS-…" ทีละชุด ยืนยันชุด A แล้วชุด B ยังเปิดอยู่ (มีทั้งเทสต์และผลในเบราว์เซอร์)

**คลาส C:** ทุก `REBAR_SET_*` ที่เป็น block รวมทิศ UNSPECIFIED

**การหลุดของ approval**
- แก้ เพิ่ม หรือลบชุด หรือแก้เรขาคณิต: ขึ้น `APPROVAL_STALE` เพราะกลไก 17.2 ครอบ `rebarSets` อัตโนมัติ
- `REBAR_DEFAULTED` ของข้อความเดิมไม่ขึ้นเมื่อแยกเป็นชุดแล้ว เพราะแต่ละชุดมีที่มาของตัวเอง

**ข้อจำกัด L1 (ตามที่อนุมัติ):** ไม่มี approval record อิสระต่อชุด "ยืนยันชุด" บันทึกผู้ยืนยัน เวลา และไฟล์แบบไว้บนชุด แต่การอนุมัติให้ปล่อยยอดยังเป็นระดับชิ้น

**Audit trail:** `rebarSets` อยู่ใน `TRACKED_FIELDS` ประวัติแสดงแบบ "ชุดเหล็ก: RS-… 6-DB12 X TOP [reviewer] → … 8-DB12 …" และย้อนได้

  - ทำครบตามแผนและตรวจในเบราว์เซอร์แล้ว: โมเดล, การคำนวณ, validation, provenance และการอนุมัติ, export, ประวัติ, UI การ์ดชุดเหล็ก
  - ยังขาดจากโจทย์: ช่อง cover และจำนวนชิ้นในส่วนเรขาคณิต, การแก้ค่าขัดแย้ง, reader ที่สร้างชุดเอง, approval record ต่อชุด
- **Safety: SAFE WITH RESTRICTIONS** (เหมือน 18d)
  - ทางชุดเข้มกว่าทางเดิม: ไม่เดาทิศหรือความยาวงอ, ไม่ปัดจำนวน, ชุดที่คิดไม่ได้ถูก block
  - ไม่มีทางใดปล่อยยอดที่ข้อมูลไม่ครบโดยไม่มีคนตรวจ
  - ข้อจำกัด pilot เดิมยังใช้ทั้งหมด และเทสต์ที่ผ่านไม่ใช่หลักฐานความแม่นยำทางวิศวกรรม

## 15. เพิ่มช่องเรขาคณิต: จำนวนชิ้นและระยะหุ้ม (2026-11-03, หลังผู้ใช้อนุมัติ)

**สิ่งที่เปลี่ยน**
- **ช่องใหม่ในหน้ารายชิ้นของฐานราก (`ReviewWorkspace.tsx`):**
  - "จำนวน (ชิ้น)" ผูกกับ `count`
  - "ระยะหุ้ม (ซม.)" ผูกกับ `coveringCm` ถ้าว่างจะแสดง placeholder "ตามสเปกโครงการ"
  - หน่วยระยะหุ้มเป็น **ซม.** ตามหน่วยที่ engine เก็บ ไม่ได้แปลงเป็น มม. ตามโจทย์ เพื่อไม่ต้องเพิ่มชั้นแปลงหน่วย
- **การตรวจจำนวนชิ้น (`qsEngine.ts`):** ต้องเป็นจำนวนเต็มบวก ข้อความเดิมระบุไว้แล้วว่า "positive finite integer" แต่โค้ดตรวจแค่ > 0 จึงทำให้ตรงกัน จำนวน 2.5 ตอนนี้เป็น REJECTED
- **การล้างช่องระยะหุ้ม:** ค่าที่ส่งเข้า engine เป็น 0 จะ block ด้วย `COVER_INVALID` ไม่กลับไปใช้ค่าสเปกแบบเงียบ ๆ (ตั้งใจ แต่ยังล้างกลับเป็น "ตามสเปก" จากช่องนี้ไม่ได้)
- **ประวัติ (`reviewLog.ts`):** บันทึก `count` และ `coveringCm` และแสดงในหน้าที่มาของฐานราก (`TYPE_FIELDS`)
