## 6.1 การอนุมัติรายชิ้นข้ามอะไรได้บ้าง (ผลจริง)

กลไกปัจจุบัน (`qsEngine.ts` release gate): `block` → ไม่ปล่อยเสมอ; มิติ NaN/ติดลบ/0 → REJECTED; **นอกนั้น approval ที่ key ตรง → AUTO_RELEASE ทุกกรณี** (approval ข้าม `warn` ได้ทั้งหมด)

| เงื่อนไข | ก่อนอนุมัติ | หลังอนุมัติ (ปัจจุบัน) | flag | ควรเป็น (ข้อเสนอ) |
|---|---|---|---|---|
| UNKNOWN (ไม่มี source record) | NEEDS_REVIEW | **AUTO_RELEASE** | PROVENANCE_UNSPECIFIED:warn | **A** — QS อนุมัติได้หลังตรวจ แต่ป้ายต้องเป็น USER_CONFIRMED ไม่ใช่ DRAWING_VERIFIED (เป็นอยู่แล้ว) |
| ฟิลด์ required "missing" แต่มีค่า | NEEDS_REVIEW | **AUTO_RELEASE** | FIELD_VALUE_UNSOURCED:warn | **B** — ต้องยืนยัน/แก้ฟิลด์นั้นก่อน (field-level) ไม่ใช่อนุมัติทั้งชิ้น |
| ฟิลด์ required missing ค่า 0 | NEEDS_REVIEW | NEEDS_REVIEW | FIELD_MISSING:block | **B** (ถูกต้องแล้ว) |
| ENGINEERING_ASSUMPTION (`assumed`) | NEEDS_REVIEW | **AUTO_RELEASE** | FIELD_ASSUMED:warn | **B** สำหรับฟิลด์ required (ต้องยืนยันฟิลด์) / **A** สำหรับสมมติฐานที่ไม่ใช่ required พร้อมเหตุผล |
| DEFAULT_VALUE (เหล็ก missing) | NEEDS_REVIEW | **AUTO_RELEASE** | REBAR_DEFAULTED:warn | **B** — ต้องกรอกเหล็กจากแบบหรือบันทึกเป็นสมมติฐานโดยชัดแจ้ง |
| ค่าขัดแย้ง (เช่น หนา 0.30 vs 0.20) | NEEDS_REVIEW | **AUTO_RELEASE** | CONFLICT:warn | **B** — ต้องเลือกค่าในฟิลด์ (ห้ามอนุมัติทั้งชิ้นโดยไม่ระบุว่าใช้ค่าใด) |
| ความมั่นใจการอ่านต่ำ (0.6) | NEEDS_REVIEW | AUTO_RELEASE | LOW_CONFIDENCE:warn | **A** |
| **ไม่ระบุเหล็กเลย** | **AUTO_RELEASE** (ไม่ต้องอนุมัติ) | AUTO_RELEASE | ไม่มี warn (เฉพาะ info: REBAR_RATIO_ASSUMED, FOOTING_HOOK_ASSUMED, COVER_ASSUMED) | **B** — ปัจจุบันเป็น **ช่องโหว่ gate** (G1): เหล็ก DB12@0.15 + งอตั้งเต็มความหนา ถูกสร้างและปล่อยเอง 12.79 กก. |
| ไม่ระบุรูปงอ (ใช้ค่าเริ่มต้น FULL_UPTURN ของสเปก) | **AUTO_RELEASE** | AUTO_RELEASE | FOOTING_HOOK_ASSUMED:info | **A** (ต้องเป็น warn ก่อน) — ช่องโหว่ G2 |
| รูปงอ UNSPECIFIED | NEEDS_REVIEW | AUTO_RELEASE | FOOTING_HOOK_UNSPECIFIED:warn | **A** พร้อมเหตุผล |
| spacing ผิด (@0) | NEEDS_REVIEW | NEEDS_REVIEW | REBAR_SPACING_INVALID:block | **C** (ถูกต้องแล้ว) |
| สเปคเหล็กอ่านไม่ได้ | NEEDS_REVIEW | NEEDS_REVIEW | REBAR_SPEC_UNPARSED:block | **B** (แก้สเปคแล้วผ่านได้) |
| **cover เกินขนาด (60 ซม. ในฐาน 0.90)** | NEEDS_REVIEW | **AUTO_RELEASE** | COVER_INVALID:warn | **C** — เรขาคณิตเป็นไปไม่ได้ (ช่วงสุทธิติดลบ) ต้องห้ามอนุมัติ — ช่องโหว่ G3 |
| มิติ NaN / ติดลบ | REJECTED | REJECTED | — | **C** (ถูกต้องแล้ว) |

**นิยามคลาส:** A = อนุมัติได้หลัง QS ตรวจ (ต้องมีเหตุผล) · B = ต้องคง NEEDS_REVIEW จนกว่าฟิลด์ที่เกี่ยวข้องถูกแก้/ยืนยันระดับฟิลด์ · C = ปฏิเสธ อนุมัติไม่ได้

**ข้อค้นพบหลัก:** การอนุมัติรายชิ้นข้ามได้ทั้ง B (ค่าขัดแย้ง, ฟิลด์ไม่มีที่มา, เหล็กค่าเริ่มต้น) และ C (cover เป็นไปไม่ได้) → QS อาจอนุมัติสมมติฐานที่ไม่เกี่ยวกับสิ่งที่ตัวเองตรวจโดยไม่รู้ตัว (ผิดกฎ Phase 5 ข้อ 8)

## 6.2 การอนุมัติระดับฟิลด์ (สภาพปัจจุบัน)

| ข้อกำหนด | ปัจจุบัน |
|---|---|
| อนุมัติฟิลด์หนึ่งไม่อนุมัติฟิลด์อื่น | **ไม่มี field-level approval** — มีเพียง `fieldSources[f] = 'reviewer'` (ยืนยันค่า) + `review` ระดับ member; การอนุมัติ member ครอบทุกฟิลด์ |
| ยืนยันมิติไม่ยืนยันสมมติฐานเหล็ก | ตารางตามเบอร์ยืนยันเฉพาะฟิลด์ที่แสดง และอนุมัติชิ้นเฉพาะเมื่อ required ครบ (R17.2) ✅ / รายชิ้น "อนุมัติ" ครอบทุกอย่าง ❌ |
| แก้ฟิลด์แล้ว approval หลุด | ✅ (R17.2: `valuesKey` ระดับ member — แก้ฟิลด์ใดก็หลุดทั้งชิ้น ไม่แยกระดับฟิลด์) |
| แก้ฟิลด์ที่พึ่งพากันแล้ว approval ที่เกี่ยวข้องหลุด | ✅ ทางอ้อม (ทั้งชิ้นหลุด) |
| เก็บค่าที่ตรวจตรงตัว | ✅ ทางอ้อม (`valuesKey` เป็นลายเซ็น ไม่ใช่ค่า; ค่าอยู่ใน log `before`) |
| AUTO_RELEASE ระดับชิ้นต้องให้ required ทุกตัวผ่าน | ❌ เฉพาะทางตาราง; รายชิ้นข้ามได้ |

## 6.3 ตัวตนผู้อนุมัติและ revision

| รายการ | ปัจจุบัน |
|---|---|
| Stable member ID | **ไม่มี** — `itemId` = `QS-{type}-{index}`; log อ้าง `indices` (ลำดับใน array) |
| Field ID / ค่าที่อนุมัติ / ค่าก่อน | log มี `changes{field, from, to}` และ `before` snapshot |
| ผู้อนุมัติ | **ไม่มี** |
| เวลา | มี (`review.at`, `entry.at`) |
| Drawing revision | **ไม่มี** (มีเพียงชื่อไฟล์ระดับโครงการ) |
| Source provenance ตอนอนุมัติ | ไม่เก็บใน approval (อยู่บน member ปัจจุบันเท่านั้น) |
| เหตุผล | `note` ไม่บังคับ |

ทดสอบตามโจทย์ (ตรวจจากโค้ด + เทสต์ R17.2):

| เหตุการณ์ | approval เดิม |
|---|---|
| สลับลำดับ member | `review` อยู่บน member object → ตามไปกับ member ✅; แต่ **log อ้าง index ผิดตัว** ❌ และ `itemId` เปลี่ยน |
| ลบ/แทรก member | เหมือนข้างบน (UI ไม่มีปุ่มลบ member; แทรกได้จาก "เพิ่มเอง"/"เพิ่มที่แนะนำ" ต่อท้าย) |
| Revision เปลี่ยน / OCR ใหม่ / reload / กู้รีวิว | กู้รีวิวเฉพาะเมื่อผลอ่านเหมือนเดิมทุกค่า ✅ (R17.2); approval ที่ค่าไม่ตรง → `APPROVAL_STALE` ✅ |

## อัปเดตหลัง Round 18c — บังคับคลาส B (2026-11-03)

**กลไก:** การอนุมัติทั้งชิ้นไม่ครอบฟิลด์ที่แบบยังไม่ยืนยัน — `fieldsApprovalCannotCover(member, flags)` ใน `qsEngine.ts` คืนฟิลด์ที่ยังเปิด; ถ้ามี gate ไม่นับ approval นั้น (คง NEEDS_REVIEW) และใส่ `APPROVAL_FIELDS_OPEN:warn` ระบุชื่อช่อง
- คลาส B: `FIELD_VALUE_UNSOURCED`, `FIELD_ASSUMED`, `FIELD_INFERRED` (ฟิลด์ required), `REBAR_DEFAULTED`, `REBAR_CODE_MINIMUM`, `REBAR_RATIO_ASSUMED` (เหล็กที่ระบบสร้างเอง) — ปิดได้เมื่อผู้ตรวจพิมพ์หรือ "ยืนยันค่า" ในช่องนั้น (`fieldSources = reviewer`) หรือพิมพ์สเปคเหล็ก
- `CONFLICT` ไม่ผูกกับช่องใด → ปิดได้เมื่อผู้ตรวจยืนยันค่า required ทุกช่องของชิ้นนั้น
- คลาส A (อนุมัติได้): ไม่มี source record, ความมั่นใจต่ำ, รูปงอ UNSPECIFIED/ASSUMED, `BEAM_SUPPORT_ASSUMED`
- approval ไม่ถูกลบ: เมื่อผู้ตรวจยืนยันช่องที่เหลือ (เปลี่ยนเฉพาะ provenance) approval เดิมกลับมามีผล; ถ้าแก้ค่า → `APPROVAL_STALE` ตามเดิม

**UI (`ReviewWorkspace.tsx`):** ปุ่ม "ยืนยันค่า" ข้างช่องที่ที่มาไม่ใช่แบบ/กริด/ผู้ตรวจ (และมีค่า) · ข้อความเหนือปุ่มอนุมัติบอกช่องที่การอนุมัติไม่ครอบ (ตามค่าที่บันทึกล่าสุด — flag เหล็กตัวเดียวครอบทั้งเหล็กหลักและปลอก จึงไม่ประเมินจาก draft)

## การตัดสินหลัง 18c

**APPROVAL SAFE WITH RESTRICTIONS (สำหรับ pilot)** — release gate ไม่ปล่อยคลาส B/C ด้วยการอนุมัติรายชิ้นอีกแล้ว ทั้งทางรายชิ้นและทางตามเบอร์ ข้อจำกัดที่ต้องบังคับใน pilot:
1. หนึ่งโครงการ หนึ่ง QS ผู้อนุมัติ — แอปไม่บันทึกชื่อผู้อนุมัติ ต้องลงนามในรายงานที่ export
2. ห้ามแก้ลำดับ/แทรกชิ้นกลางรายการหลังเริ่มตรวจ (log อ้าง index; การเพิ่มต่อท้ายไม่กระทบ)
3. revision แบบใหม่ = อ่านใหม่และตรวจใหม่ (กู้รีวิวได้เฉพาะเมื่อผลอ่านเหมือนเดิมทุกค่า)
4. ตัวเลข false release 0 ของ benchmark ยังไม่ใช่หลักฐานบนข้อมูลที่มี provenance — benchmark ไม่มี source record ทุกชิ้นจึงรอตรวจหมด
5. คลาส A (ไม่มีหลักฐาน, ความมั่นใจต่ำ, รูปงอไม่ระบุ, เสารองรับสมมติ) อนุมัติได้ด้วยการตัดสินของ QS — ควรบังคับเขียนหมายเหตุ (ยังไม่บังคับ)

**สิ่งที่ทำ**
- **ชื่อผู้ตรวจ:** ช่อง "ผู้ตรวจ" บนหน้าตรวจทาน (จำไว้ในเบราว์เซอร์นี้) — **อนุมัติ/ไม่นับไม่ได้ถ้าไม่มีชื่อ** (รายชิ้น: เคอร์เซอร์ย้ายไปช่องชื่อ ค่าที่พิมพ์ไม่หาย; ตามเบอร์: ยืนยันค่าได้แต่ไม่อนุมัติ; `App.handleUpdateMembers` กันซ้ำอีกชั้น) ชื่อเป็นข้อความที่พิมพ์ **ไม่ได้ยืนยันตัวตน** — ระบุไว้ใน Excel
- **Revision:** เปิดไฟล์ PDF/DXF → `ชื่อไฟล์ · SHA-256 16 หลักแรก` (Web Crypto; ถ้าเบราว์เซอร์ไม่อนุญาต เช่น http ที่ไม่ใช่ localhost จะบันทึกว่า "ไม่มี hash") ตัวอย่าง/ชุดข้อมูลไม่มี revision
- **ตราประทับ:** ทุกการตัดสิน (`review.by`, `review.revision`) และทุกรายการใน log (`by`, `revision`) ประทับที่จุดเดียวใน `App.tsx`; การยืนยันค่าทางตารางที่ไม่เปลี่ยนการตัดสินไม่ประทับทับการตัดสินเดิม
- **Excel:** แผ่น 7 มีแถวหัว "ไฟล์แบบ: …" + คอลัมน์ ผู้ตรวจ / ไฟล์แบบที่ตรวจ; แผ่น 8 เปลี่ยน "จำนวนชิ้น" เป็น **รหัสชิ้น** (`QS-C-002` …) + ผู้ตรวจ / ไฟล์แบบ

**ไม่ทำ stable `memberId` (ตัดสินจากโค้ด ไม่ใช่ข้ามงาน):** ตรวจทุกทางที่แก้รายการชิ้น (`commitMembers`/`setActiveMembers`) — มีแค่ แก้ค่าตามตำแหน่ง, เพิ่มต่อท้าย (เพิ่มเอง/เพิ่มที่แนะนำ), ย้อนการเพิ่มได้เฉพาะชุดท้ายสุด (`canUndo`); ไม่มีลบ/สลับ/แทรกกลาง และการกู้รีวิวทำเฉพาะผลอ่านเหมือนเดิมทุกค่า → ตำแหน่งชิ้นคงที่ตลอดอายุ log จึงใช้เป็น ID ได้ ช่องโหว่จริงคือ Excel ไม่บอกว่า log แตะชิ้นไหน → แก้แล้ว (รหัสชิ้น) · ถ้าในอนาคตเพิ่มปุ่มลบ/เรียงชิ้น ต้องทำ `memberId` ก่อน (เขียนไว้ใน comment ของ `ReviewLogEntry.indices`)

**ตรวจ:** `npm test` 150/150 (เทสต์ใหม่ "Round 18d" อ่าน Excel ที่สร้างจริง: แผ่น 7 มีชื่อผู้ตรวจ/ไฟล์, แผ่น 8 มีรหัสชิ้น) · tsc/build ผ่าน · benchmark ไม่เปลี่ยน (0/28 auto, 0 false release) · parity 22/22 เหมือนเดิม · **เบราว์เซอร์ (Villa B1):** ไม่มีชื่อ → กดอนุมัติแล้ว "ตรวจแล้ว 0", เคอร์เซอร์อยู่ช่องชื่อ, ค่าเหล็กที่พิมพ์ยังอยู่; กรอกชื่อแล้วอนุมัติ → "ตรวจแล้ว 1", ชื่อจำใน localStorage; console ไม่มี error · **ไม่ได้ทดสอบในเบราว์เซอร์:** การเปิดไฟล์จริงเพื่อดู hash และการดาวน์โหลด Excel (ครอบด้วย unit test ของ workbook เท่านั้น)
