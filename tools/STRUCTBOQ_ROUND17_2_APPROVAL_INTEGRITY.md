## 2. การอนุมัติระดับฟิลด์ vs ระดับ member

### สภาพปัจจุบัน

| ช่องทาง | สิ่งที่ผู้ใช้เห็น | สิ่งที่ระบบทำ |
|---|---|---|
| รายชิ้น "บันทึก + อนุมัติ" (`ReviewWorkspace.decide('approved')`) | ฟิลด์ทั้งหมดของชิ้น + รายการ flag | ฟิลด์ที่แก้ → `reviewer`; member → `approved` → **AUTO_RELEASE แม้มี warn ค้าง** (เฉพาะ block ที่หยุดได้) |
| ตามเบอร์ "ยืนยันตามที่อ่านได้" (`SectionTable.confirm`) | **เฉพาะฟิลด์หน้าตัด** (คาน: กว้าง, ลึก, เหล็กบน/ล่าง/ปลอก; เสา: ด้าน X/Y, เหล็ก) | ฟิลด์ที่แสดงและเป็น `assumed`/`inferred` → `reviewer`; **ทุก member ของเบอร์ → `approved`** แม้ช่วงคาน (c/c), ความกว้างเสารองรับ, ความสูงเสา **ไม่ได้แสดง** |

### ปัญหาที่ยืนยันแล้ว

- **F1 (ยืนยันในเบราว์เซอร์):** โครงการตัวอย่าง Villa — เปิด "ตามเบอร์" เลือก B2 ตารางแสดงเฉพาะ กว้าง/ลึก/เหล็กบน/เหล็กล่าง/เหล็กปลอก กด "ยืนยันตามที่อ่านได้" → B2 เป็น "อนุมัติแล้ว — ยืนยันหน้าตัด B2" และนับใน "ตรวจแล้ว" ทั้งที่ช่วง c/c และเสารองรับไม่เคยถูกแสดง → **การยืนยันหน้าตัดทำให้ฟิลด์ที่เป็น ENGINEERING_ASSUMPTION / UNKNOWN ผ่านไปด้วย** (ผิดเงื่อนไข Task 2)
- **F2:** การอนุมัติระดับ member ไม่ต้องการให้ required field ผ่านเงื่อนไขครบ — approval ข้าม warn ทุกชนิด (ตามออกแบบ Round 12: "QS รับผิดชอบ") แต่เมื่อไม่มีตัวตนผู้อนุมัติ (หัวข้อ 1) การข้ามนี้ไม่มีผู้รับผิดชอบที่ระบุได้

ไม่ได้แก้ F1/F2 ในรอบนี้ — ต้องแยกการยืนยันฟิลด์ออกจากการอนุมัติ member = เปลี่ยนโครงสร้าง (หัวข้อ 7)

## 7. ข้อเสนอการออกแบบ (ต้องเปลี่ยนโครงสร้าง Approval — หยุดรอคำสั่ง)

1. **ผูก approval กับค่า (ปิด R3, ไม่ต้องพึ่ง UI):** `review` เก็บ `valuesKey` = ลายเซ็นของฟิลด์ที่มีผลต่อปริมาณ ณ เวลาอนุมัติ; `calculateMember` ถือว่า approval เป็นโมฆะถ้าลายเซ็นปัจจุบันไม่ตรง → NEEDS_REVIEW พร้อม flag `APPROVAL_STALE` (เข้มขึ้น ไม่ผ่อน gate)
2. **แยกยืนยันฟิลด์ออกจากอนุมัติ member (ปิด R2):**
   - ยืนยันฟิลด์ = เปลี่ยน `fieldSources[f]` เป็น `reviewer` **เฉพาะฟิลด์ที่แสดงและผู้ใช้ยืนยัน**
   - อนุมัติ member ได้เมื่อ required fields ทุกตัว (CRITICAL_FIELDS + `support` ของคาน) เป็น `drawing`/`grid`/`reviewer` และไม่มี block; ถ้าไม่ครบ ปุ่มอนุมัติแสดงรายการฟิลด์ที่ยังไม่ยืนยัน
   - ตารางตามเบอร์: "ยืนยันหน้าตัด" ยืนยันเฉพาะฟิลด์หน้าตัด ไม่ตั้ง `review` — ชิ้นยังรอจนช่วง/เสารองรับถูกยืนยันในรายชิ้น
   - ต้องตัดสิน: approval ระดับ member ยัง "ข้าม warn ได้" หรือไม่ (ข้อเสนอ: ข้ามได้เฉพาะ warn ที่ไม่ใช่ฟิลด์ required และต้องมีเหตุผล)
3. **Audit trail (ปิด R1 บางส่วน):** `review` เพิ่ม `by` (ชื่อ QS ที่กรอกตอนเริ่มรีวิว), `revision` (ชื่อไฟล์ + hash/วันที่ revision), `values` (ค่าที่อนุมัติ), `memberKey` ถาวร (เช่น `type:tag@grid`); log อ้าง `memberKey` แทน index — **ข้อจำกัดที่ต้องรับรู้:** ในแอปเบราว์เซอร์ที่ไม่มี login ตัวตนที่กรอกเองตรวจสอบไม่ได้ จะเป็นหลักฐานทางวิชาชีพได้ต้องมีระบบบัญชีผู้ใช้หรือลายเซ็นนอกระบบ
4. **ลายเซ็นการกู้รีวิว (ปิด R4):** ใช้ค่าทั้ง member ของผลอ่านใหม่ (ยกเว้น `review`) แทนรายการฟิลด์ — เปลี่ยน 1 บรรทัด ไม่ต้องเปลี่ยนโครงสร้าง (เสนอแก้แยกได้)

ลำดับที่แนะนำ: 4 → 1 → 2 → 3

### ข้อ 4 — กู้รีวิวเฉพาะเมื่อผลอ่านเหมือนเดิมทุกค่า (ปิด R4)

### ข้อ 1 — ผูก approval กับค่า (ปิด R3)
- `qsEngine.ts`: `ReviewDecision.valuesKey`; `approvalKey(m)` = ทุกฟิลด์ของ member ยกเว้น `review` และ `provenance` เรียงคีย์คงที่; `approvalFor(m, note)` สร้าง approval พร้อม key
- `calculateMember`: approval ที่ key ไม่ตรง (ค่าเปลี่ยนหลังอนุมัติ **หรือไม่มี key เลย**) ถือว่าไม่มี approval + warn `APPROVAL_STALE` → NEEDS_REVIEW; `review` ใน item ผลลัพธ์เป็น `undefined` ทำให้ UI, ปร.4, Excel ไม่นับเป็น "ตรวจแล้ว"
- `computeProject`: การยกเว้นตรวจซ้ำ (duplicate) และพื้นซ้อน ใช้ approval หลังตรวจ key แทน approval ดิบ
- `provenance` ไม่อยู่ใน key โดยตั้งใจ: QS ยืนยันฟิลด์ (เปลี่ยน `fieldSources` เป็น `reviewer`) ไม่ทำให้ approval หลุด
- "ไม่นับ" (rejected) ไม่ผูก key — ยังคงไม่นับแม้ค่าเปลี่ยน (ฝั่งปลอดภัย)
- ผู้สร้าง approval: `ReviewWorkspace.decide('approved')` และ `SectionTable.confirm` ใช้ `approvalFor` กับค่าหลังแก้
- เทสต์: `pipeline.test.ts` และ `releaseGate.test.ts` เปลี่ยน approval ที่เขียนมือเป็น `approvalFor(member)` — เหตุผลทางวิศวกรรม: approval ต้องระบุค่าที่อนุมัติ; เทสต์ใหม่ "Round 17.2: an approval covers only the values it was given on" ตรวจ: approval ปกติ → AUTO_RELEASE, ยืนยันฟิลด์ภายหลัง → ยังผ่าน, เปลี่ยน width / hook / ปลอกคู่ / clear span → NEEDS_REVIEW + `APPROVAL_STALE`, approval ไม่มี key → NEEDS_REVIEW, rejected → REJECTED; `reviewLog.test.ts` เพิ่มกรณี hook shape

## 9. แก้ R2 — ยืนยันหน้าตัดไม่อนุมัติฟิลด์ที่ไม่แสดง (2026-11-03, หลังผู้ใช้อนุมัติ)

- `qsEngine.ts` `unconfirmedRequiredFields(m)`: คืนฟิลด์ required (CRITICAL_FIELDS ของประเภท + `support` ของคานเมื่อมี source) ที่ source ไม่ใช่ `drawing`/`grid`/`reviewer`; ไม่มี source record → ทุกฟิลด์ required ยังไม่ยืนยัน
- `SectionTable.confirm`: ยืนยันเฉพาะฟิลด์ที่ตารางแสดง (เดิม); **อนุมัติ member เฉพาะเมื่อ `unconfirmedRequiredFields` ว่างและมิติครบ** — ถ้ายังมีช่วงคาน/ความสูงเสา/เสารองรับที่ไม่ได้ยืนยัน ชิ้นนั้นอยู่ในคิวรายชิ้นต่อ (approval เดิมคงไว้ และจะหลุดเองถ้าค่าเปลี่ยน ตามข้อ 1)
- ไม่เปลี่ยนความหมาย provenance; การอนุมัติรายชิ้น ("บันทึก + อนุมัติ") ยังเป็นการตัดสินของ QS ที่ข้าม warn ได้ตามเดิม (ข้อเสนอ 2 ส่วนที่เหลือ — ยังไม่ทำ)
