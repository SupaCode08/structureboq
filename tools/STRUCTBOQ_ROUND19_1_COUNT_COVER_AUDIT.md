**วันที่:** 2026-11-03 · **สถานะ:** แก้ตามแผนหัวข้อ 4 แล้ว (ผู้ใช้อนุมัติ) — ผลอยู่หัวข้อ 6–12 · หัวข้อ 1–5 คือ audit ก่อนแก้ (คงไว้ตามเดิม)

## 1. คำตอบ 5 ข้อ

**1. Count หมายถึงอะไร**
`ExtractedMember.count` คือ**จำนวนฐานรากที่เหมือนกันซึ่งรายการนี้แทน** (reader ตั้งเป็น 1 ต่อตำแหน่งในผัง ส่วนตัวอย่างและ "เพิ่มเอง" อาจเป็น 4 เป็นต้น) ระบบมีสามความหมายแยกกันอยู่แล้ว ไม่ได้ใช้ตัวแปรเดียวกัน:

| ความหมาย | field |
|---|---|
| จำนวนฐานราก | `member.count` |
| จำนวนเหล็กต่อฐานต่อทิศ | `RebarSet.quantity` (หรือตัวเลขใน `bottomRebar` เช่น `6-DB12`) |
| จำนวนชุดเหล็ก | `rebarSets.length` (ไม่เข้าสูตรปริมาณใดเลย) |

→ **ความหมายไม่กำกวม จึงไม่ต้องหยุด** ตามเงื่อนไขของโจทย์

**2. Count คูณกับอะไร** (`qsEngine.ts`) คูณครั้งเดียวต่อรายการ:
- คอนกรีต: `count × w × d × t` (`:1493–1494`)
- ไม้แบบ: `count × 2(w+d) × t` (`:1518`)
- lean, ทราย, ขุดดิน, เข็ม: คูณ count (`:1519–1524`)
- เหล็ก: `pushBarItem(count × n …)` ทั้งทางข้อความ (`:1014–1015`) และทาง RebarSet (`:915`)
- ยอดโครงการ (`computeProject`): **รวมค่าของรายการที่คูณแล้ว ไม่คูณ count ซ้ำ**
- Excel: แสดง count เป็นคอลัมน์ ส่วนปริมาณเป็นค่าที่คูณแล้ว ไม่คูณซ้ำ
- **ไม่พบการคูณซ้ำ** (มีเทสต์ยืนยันในหัวข้อ 4)

**3. Cover หักจากมิติไหน** หักจากทุกด้าน:
- ความยาวเหล็ก (run) = มิติแนวเหล็ก − 2c
- ช่วงกระจายเหล็ก (spread) = มิติตั้งฉาก − 2c
- ขางอตั้ง = ความหนา − 2c

การตรวจเรขาคณิต: block เมื่อ 2c ≥ กว้าง, ยาว หรือหนา (18b)

**4. Cover ใช้กับทุก RebarSet หรือไม่** ใช้ — มี **ค่าเดียวต่อชิ้น** ใช้กับทุกชุด ทุกชั้น ทุกด้าน ไม่มี cover แยกชั้นบนกับล่าง หรือแยกด้านข้างกับก้นฐาน (ข้อจำกัด)

**5. Cover จากแบบ สเปก และที่ผู้ใช้กรอก มี provenance แยกกันหรือไม่** **ไม่แยก และป้ายผิด** (ดู F1–F3)

| F6 | การ์ด RebarSet แสดง "80 เส้น" เป็นยอดรวมทุกฐาน (count × เส้นต่อฐาน × ทิศ) อยู่ข้างช่อง "จำนวน (เส้น/ทิศ)" ที่เป็นต่อฐาน ส่วน Excel "จำนวนเส้น (Pieces)" ก็เป็นยอดรวมทุกฐาน | browser R19 | ต่ำ — ตัวเลขถูกแต่ป้ายกำกวม |
| F7 | สเปกโครงการไม่บันทึกว่าค่าระยะหุ้มมาจากไหน (หมายเหตุในแบบ, ผู้ใช้ตั้งใน MaterialSpecsModal หรือค่าเริ่มต้น) — `MaterialSpecs.footingCoveringCm` เป็นตัวเลขเปล่า ค่าเริ่มต้นจึงเท่ากับ 5.0 เสมอ | `DEFAULT_MATERIAL_SPECS.footingCoveringCm = 5.0` | รากของ F1/F2/F4 |

ตรวจแล้ว**ไม่มีปัญหา**:
- ค่าระยะหุ้ม 0, ติดลบ, NaN, Infinity และ > 20 ซม. → `COVER_INVALID:block` (18a)
- 2c ≥ หน้าตัดหรือความหนา → `COVER_EXCEEDS_DIMENSION:block` (18b)
- จำนวนชิ้นที่ไม่ใช่จำนวนเต็มบวก → REJECTED (Round 19 หัวข้อ 15)
- แก้ `coveringCm` หรือ `count` ที่ระดับ member → `APPROVAL_STALE` (17.2)

## 3. Root cause
- **F1/F2/F7:** `resolveMemberCoverM` เดาที่มาจาก "ค่าเท่าค่าเริ่มต้นหรือไม่" เพราะสเปกไม่เก็บที่มา
- **F3:** ช่องเดียว (`coveringCm`) ใช้รับทั้งค่าจากแบบระดับชิ้น (reader ไม่เคยเขียนช่องนี้) และค่าที่ผู้ตรวจพิมพ์ แต่ resolver ไม่อ่าน `fieldSources`
- **F4:** `COVER_ASSUMED` เป็น info ซึ่งไม่กักการปล่อย
- **F5:** approval ผูกกับ input ของ member ไม่ใช่ค่าที่ใช้คำนวณจริง

## 4. แผนแก้ (รออนุมัติ)

**4.1 Engine (`qsEngine.ts`)**
- **Count:** ไม่แก้สูตร
- **Cover:** `resolveMemberCoverM` รับที่มาเพิ่ม (ไม่แตะการคำนวณ ระยะหุ้มที่ได้ยังเป็นค่าเดิมทุกกรณีที่ถูกต้อง) และคืน `source`:

| source | เมื่อไร |
|---|---|
| `drawing` | ระยะหุ้มระดับชิ้นที่ `fieldSources.cover = drawing` |
| `manual` | ระยะหุ้มระดับชิ้นที่ผู้ตรวจกรอก → แก้ F3 |
| `drawing_notes` | สเปกโครงการที่มาจากหมายเหตุในแบบ |
| `project_spec` | ผู้ใช้ตั้งในหน้าสเปก |
| `default` | ไม่มีที่มาใดเลย |

  ที่มาของสเปกเก็บใน `MaterialSpecs.coverSources?: Partial<Record<'footing' \| 'column' \| 'beam' \| 'slab', 'drawing_notes' \| 'user'>>` (optional, ค่าเดิมไม่หาย) ตั้งโดย `applyGeneralNotesToSpecs` และ `MaterialSpecsModal` ตอนบันทึก → แก้ F1, F2, F7
- **โหมดระยะหุ้มต่อชิ้น:** `coverMode?: 'FROM_DRAWING' | 'FROM_PROJECT_SPEC' | 'MANUAL'`
  - ไม่ระบุโหมด: ลำดับความสำคัญเดิม (ชิ้น > สเปก > ค่าเริ่มต้น) แต่ป้ายถูกต้อง
  - `FROM_DRAWING`: ใช้ค่าระดับชิ้นจากแบบ ถ้าไม่มีใช้ค่าจากหมายเหตุในแบบ ถ้าไม่มีทั้งคู่ → block "แบบไม่ให้ระยะหุ้ม"
  - `FROM_PROJECT_SPEC`: ใช้สเปก (ถ้าสเปกเป็นค่าเริ่มต้น → ขั้นถัดไป)
  - `MANUAL`: ต้องเป็นค่าบวก finite ≤ 20 ซม. ไม่เช่นนั้น block (มีอยู่แล้ว)
- **F4:** ฐานรากที่ใช้ระยะหุ้ม `default` → `COVER_ASSUMED` เป็น **warn เฉพาะ FOOTING** (คลาส A — QS อนุมัติได้หลังตรวจ) ชิ้นประเภทอื่นคงเป็น info (ขอบเขตรอบนี้คือฐานราก)
  - ผลกระทบ: ฐานรากที่แบบไม่มีระยะหุ้มทุกตัวจะเข้าคิวรอตรวจ
- **F5:** การอนุมัติบันทึกระยะหุ้มที่ใช้จริง (`review.coverM`) `calculateMember` เทียบกับค่าที่ resolve ได้ตอนนี้ ถ้าต่าง → `APPROVAL_STALE` (ใช้กลไกเดิม)
  - ใช้กับทุกประเภทชิ้น เพราะเป็นช่องโหว่ของ gate เดียวกัน
  - approval เก่าที่ไม่มี `coverM` จะยังใช้ได้ตามเดิม (ไม่ทำให้หลุดทั้งหมด)
  - **ไม่ครอบ** ค่าอื่นในสเปก (รูปงอค่าเริ่มต้น, % เผื่อเสีย, ราคา) — ระบุเป็นข้อจำกัด ไม่แก้ในรอบนี้

**4.2 UI (`ReviewWorkspace.tsx`)**
- ช่อง "ระยะหุ้ม" ของฐานราก: ตัวเลือกโหมด 3 แบบ + ช่องกรอก (เปิดใช้เฉพาะ MANUAL) + "ใช้จริง: X ซม. · ที่มา: …" (จากผลคำนวณ)

**4.4 เทสต์** เพิ่มข้อ 1–14 ของโจทย์ ทุกข้อตรวจค่าผลลัพธ์จริง

**ความเสี่ยงต่อระบบเดิม**

## 12. ข้อจำกัดที่เหลือ
- การหลุดของ approval เมื่อเปลี่ยนสเปกครอบเฉพาะ**ระยะหุ้ม** ค่าอื่นในสเปก (รูปงอค่าเริ่มต้น, % เผื่อเสีย, ราคา) ยังเปลี่ยนหลังอนุมัติได้โดย approval ไม่หลุด
- approval ที่ทำก่อน 19.1 หรือผ่าน `approvalFor` นอกแอป (ไม่มี `coverM`) ไม่ได้รับการป้องกันนี้
- ระยะหุ้มมีค่าเดียวต่อชิ้น ใช้กับทุกชุดเหล็ก ทุกชั้น ทุกด้าน (ก้นฐานกับด้านข้างหรือชั้นบนไม่แยกกัน)
- reader ยังไม่อ่านระยะหุ้มระดับชิ้น โหมด "จากแบบ" จึงพึ่งหมายเหตุทั่วไปในแบบเป็นหลัก
- ผลวัดการดึงหมายเหตุบนแบบจริงยังไม่ได้วัดในรอบนี้
- เมื่อสลับจาก "กรอกเอง" ไปโหมดอื่น ค่าที่เคยกรอกยังอยู่ใน member (ไม่ถูกใช้ แต่เห็นได้ในประวัติ)
- หน้าสเปกโครงการแก้ได้เฉพาะระยะหุ้มรวม (`legacy_spec`) ยังไม่มีช่องระยะหุ้มของฐานรากโดยเฉพาะ
- ฐานรากที่แบบไม่ให้ระยะหุ้มจะไม่ AUTO_RELEASE อีก ทำให้คิวรอตรวจยาวขึ้น (ตั้งใจ)
